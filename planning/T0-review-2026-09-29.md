## 四项裁决

### 1. 受保护改动范围：核定必要路径，但修订方案

核定下一轮为本次浏览器计算需求实施以下必要改动：

- `dashboard/src/DataAppShell.jsx`：新增明确的静态内存分析提交接口。限制在非 hosted 分支，保持 app id、surface 和产品权限不变；不能无条件暴露可随意修改整个壳层的 setter。
- `dashboard/src/use-data-app.js`：修复静态快照更新后查询仍停在初始值的问题。保留 hosted/queryDataStore 的已有行为，并测试更新查询与现有编辑流程；不预先认可报告中的“一行替换”就是最终正确实现。
- `dashboard/package.json`、`dashboard/package-lock.json`：仅增加本次选定解析依赖并锁定，不顺带升级 React/Vite 等无关依赖。
- `dashboard/protected-runtime.json`：仅由逐路径授权脚本生成更新。

这属于用户已要求的改造协调范围核定，不需要再为相同路径重复询问。若发现还需修改 Runtime、构建脚本、Vite配置等，先提交具体原因和差异供协调核定，不能扩大授权。

先修复缺失的 hosting 基准文件，再修改上述路径。修改后在 dashboard 目录使用已安装 Node 运行：

```powershell
$env:DATA_APP_USER_CONFIRMED='1'
node scripts/authorize-protected-change.mjs --confirmed --scope src/DataAppShell.jsx --scope src/use-data-app.js --scope package.json --scope package-lock.json --reason '用户要求浏览器计算改造，由协调审核核定静态分析提交与解析依赖的必要改动'
```

scope 必须与实际变更保护文件逐一一致，未修改的路径不应列入；不要把清单自身当源文件 scope。授权后完整校验并以 `--source` 构建；禁止普通预编译构建悄悄忽略这些源文件改动。

### 2. 解析路线：选择成熟 OOXML 库，保留受测 CSV 代码

选择 `read-excel-file@9.3.10` 作为 OOXML 解析候选的实施基线，不继续将自研 ZIP/XML 解析器作为生产主路径。原自研代码可留作明确标记的 T0 实验材料，不能与正式路径各维护一份业务解释。

已独立查询 npm 官方元数据：9.3.10 为 MIT，声明依赖 saxen、fflate、worker-f、unzipper-esm，并提供 browser/web-worker 导出。顶层用精确版本，完整传递依赖的实际解析版本及 integrity 写入 lockfile，审核报告列出；不得只写顶层版本就声称全部锁定。

依据：现在已确定动态提交需要源码构建，因此“为了避免源码构建而自行维护 ZIP/XML”不再成立。选择库是降低维护范围，不代表该库已通过本项目验收。

CSV 严格编码、文件哈希、表头、字节限额继续由业务适配层负责。必须额外验证 active 工作表回退、1900/1904 日期、公式缓存、OOXML 格式 XLS、真实格式合成文件、实际解压上限，以及 browser/Worker 构建入口。不能默认库的首表读取等于 active。若需直接使用传递依赖的 API，应将其列为明确的直接依赖并报告，不依赖偶然提升到顶层的 node_modules。
