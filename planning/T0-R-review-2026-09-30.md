## Spec：2 项实现与夹具问题

### P1 / G0 阻断：实际展开限额没有真正中止解压

位置：`dashboard/src/content/calculation/table-reader.mjs:176–200`。

超限时回调仅设置 `failure` 并 return；外层仍一次性将整个压缩包送入 `unzipper.push(bytes,true)`，后续条目继续解压，最后才抛错。单个输出块在检查之前也可能已远超 limit。测试只检查最终抛 RangeError，无法证明资源受限。

独立合成复现：2 MB + 3 MB 两个高度压缩条目，压缩包 5097 字节，limit=1000。监测锁定版本解压器实际输出：

```json
{"compressedBytes":5097,"limit":1000,"emitted":5000000,"calls":2,"largest":3000000}
```

最后抛错不等于安全中止。报告“流式超限中止”的描述目前不成立。

**修复要求：** 实现可中断、有限输出块的展开计量，达到限制后不再推进后续条目；明确单次临时分配的上界。仅把输入切成任意大块仍不足以证明输出分配上界，应验证所用解压 API 的实际行为。测试须记录后续条目不被展开及受控最大输出，而不是只断言最终报错。继续使用有限大小合成反例，不生成耗尽内存的大文件。

### P2：夹具先写错列，导致报告误判两个解析器

位置：`tests/fixtures/browser/spike/generate.mjs:124`：

```js
cellXml({ ...cell, column }, rowNumber)
```

循环索引覆盖了显式指定的 `cell.column`，因此：

- `gaps.xlsx` 实际是 A2=a1、B2=c1、A3=c2，不存在宣称的 A2/C2/C3 空列场景。
- `bounds-wide.xlsx` 的末列实际为 C，并非 XFD。
- 对应通过的测试固化了错误夹具，不能证明稀疏列/XFD 行为。

用 openpyxl 独立写出真正 A2=a1、C2=c1、C3=c2，Python 和新 JS 都返回：

```text
[['A','B','C'], ['a1',null,'c1'], [null,null,'c2']]
```

**修复要求：** 修正生成器，重新生成相关二进制夹具/哈希/预期，并直接检查压缩包内 XML 确实含 C2、C3、XFD 列引用。修正报告 §7.3 和 README，不再称为“基线共同压缩缺陷”。无需改 Python，也无需由用户重新选择空值业务口径。T1 应冻结“保留空中间列，不错位映射表头”。
